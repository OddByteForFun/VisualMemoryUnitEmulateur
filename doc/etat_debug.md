1. Gestion graphique (rendu)
LC86000-core : rendu direct depuis la XRAM, chaque frame, côté hôte.
- renderLcd() (main.zig:356) lit la XRAM via getXramByte() (main.zig:391 → banque 0 pour lignes 0-15, banque 1 pour 16-31, banque 2 pour les icônes) et dessine 48×32 pixels à l'échelle 10 (main.zig:367). Le rendu est systématique : rl.beginDrawing(); renderLcd(); rl.endDrawing() (main.zig:195-203) tourne toujours à 60 FPS, quel que soit l'état du CPU.
- Important : les registres de contrôle LCD sont simulés comme des no-ops — MCR (0x20), VCCR (0x27), STAD (0x22) ne font rien (lc86K.zig:758-760). Donc il n'y a pas de machine à état de rafraîchissement matériel (pas de vblank, pas de ghosting, pas de gating par MCR bit3 / VCCR bit7).
Dans libevmu c'est très différent : il existe un moteur de rafraîchissement indépendant et piloté par les ticks (EvmuLcd_IBehavior_update_, evmu_lcd.c:454-481) à 83/166 Hz (EVMU_LCD_REFRESH_TICKS_83HZ_), avec gating par MCR bit3 (refresh control) et VCCR bit7 (screen enable), plus gestion de ghosting. LC86000-core n'a rien de tout ça.
→ Conséquence directe : chez toi, l'écran ne change que si le BIOS/jeu réécrit la XRAM. Aucune logique périphérique ne rafraîchit ou ne gèle l'affichage.
2. Interruptions
- servicePendingInterrupt() (lc86K.zig:457) : chaîne de priorité INT2 → INT3 → T0H → T1 → P3 → Maple, push du PC sur la pile ROM-bank0, saut au vecteur (0x13/0x1B/0x23/0x2B/0x43/0x4B). Vérifie EA, interrupt_depth==0, interrupt_blocked.
- requestLevelDrivenInterrupts() (lc86K.zig:450) est vide — le flag source P31INT est posé une fois par frame dans updateButtons() (voir §4).
- L'appel se fait après chaque instruction via step() (decode.zig:267-268).
Point critique : en mode continuous (P32INT=1), updateButtons pose P31INT une fois par frame, puis servicePendingInterrupt peut déclencher l'IRQ P3 à chaque instruction pendant les 100 000 cycles de la frame, tant que l'ISR n'a pas effacé P31INT (lc86K.zig:540 laisse le flag posé « jusqu'à ce que l'ISR le efface »). C'est un candidat n°1 pour le gel d'écran (voir §6).
3. Mise à jour de l'affichage
- Aucun des 3 projets n'implémente de vsync/vblank matériel. libevmu a un refresh périodique tick-driven; DreamPotato et toi rafraîchissez implicitement à chaque frame hôte.
- Timing du base timer : dans initBiosRtc, BTCR=0x41 (lc86K.zig:353) → BT0_CYCLE bit7=0 → INT3 tous les 16384 ticks fBST ≈ 16384×183 ≈ 3M cycles CPU ≈ 0,5 s (les constantes sont CPU_FREQ=6MHz, FST_FREQ=32768). Beaucoup de jeux VMU calent leur boucle d'affichage sur l'INT3 du base timer. À ce rythme, l'écran ne se met à jour que ~2×/s — c'est probablement perçu comme un « manque de rafraîchissement ».
4. Gestion des touches
- updateButtons() (main.zig:401) est appelé une seule fois par frame hôte, avant la boucle de 100 000 cycles (main.zig:142). L'état des boutons est donc figé pendant toute la frame.
- Il mappe clavier → cpu.p3_buttons (actif-low) ; loadSFR(SFR_P3) (lc86K.zig:697) retourne cet état. Le flag P31INT est posé si un bouton est pressé et P32INT=1 (main.zig:435-440) ; P3 est réinitialisé à 0xFF à chaque frame (donc à peine pressé, p3_buttons redevient 0xFF si la touche est relâchée).
Différence clé avec libevmu : là-bas le gamepad est pollé à chaque instruction (EvmuGamepad__IBehavior_update_, appelé dans evmu_cpu.c:585), et pollButtons_ gère aussi le réveil depuis HALT et le break de HOLD. Chez toi le polling une fois/frame + le fait que p3_buttons soit en « actif-low » sans maintien pendant la frame peut faire rater un appui au code du jeu.
5. Implémentation du BIOS et d'un ROM
- Chargement : BIOS → rom (64KB pad) ; jeu → cpu.flash (bloc 0). initVmuFlash() (main.zig:242) crée le FS FAT8 (root 255, FAT 254, dir 241-253, jeu en bloc 0) ; initBiosRtc() (main.zig:315) écrit la date BCD en RAM, configure les SFR (IE=0xFF, MCR=0x08, VCCR=0x80, P3INT=0xFD, BTCR=0x41…) et pose pc = 0x2E1 pour sauter la requête de date série Dreamcast.
- Cpu.reset() (lc86K.zig:132) remet PC=0 et le CPU en banque ROM, puis initBiosRtc force PC=0x2E1 (main.zig:106-111).
- checkBiosPhase() (lc86K.zig:545) trace les phases BIOS 0x200→0x3E1, mais comme on démarre à 0x2E1, les phases d'init 0x200-0x294 sont contournées.
6. Ton problème de rafraîchissement d'écran sur touche — causes probables
Hypothèses à vérifier dans l'ordre (de la plus probable) :
1. Tempête d'IRQ P3 → gel du code du jeu. Avec P32INT=1, P31INT reste posée et servicePendingInterrupt (appelé à chaque instruction) déclenche l'IRQ P3 sans arrêt tant que l'ISR ne l'efface pas. Si l'ISR ne la vide pas, le CPU passe ses 100 000 cycles à servir P3 et le jeu ne déroule jamais sa logique → l'écran ne se met pas à jour. Vérifie que l'ISR P3 (vector 0x4B) efface bien P31INT, et si ce n'est pas le cas, efface-le côté émulateur comme le fait le matériel (une fois servie, P31INT = 0).
2. Timing du base timer (INT3) trop lent. À ~0,5 s par INT3 (BTCR cycle 16384), tout jeu dont la boucle d'affichage dépend de l'INT3 rafraîchit très lentement, et presser une touche ne change rien tant que l'INT3 n'est pas passé. Compare avec ce que le BIOS réel configure normalement.
3. Polling des touches une fois par frame + état non maintenu. Le jeu peut ne jamais « voir » l'appui s'il teste P3 entre deux updateButtons. Le passage d'état (pressé puis 0xFF) en une seule frame peut aussi casser une détection de front.
4. Pas de machine à état LCD. Aucun périphérique ne force la puce à « montrer » la nouvelle XRAM ; tout dépend du code invité qui écrit la XRAM. Si le jeu attend un timing matériel qui n'existe pas chez toi, rien n'est affiché.
7. Dois-tu démarrer sur le BIOS ou sur le jeu ?
→ Sur le BIOS, et c'est exactement ce que font les trois implémentations :
- libevmu : EVMU_BIOS_SKIP_DATE_TIME_PC = 0x2e1 (evmu_rom.h:47) ; EvmuRom_setDateTime() saute le query série puis laisse le BIOS continuer son boot/menu qui lance le jeu depuis le FS flash.
- DreamPotato : Vmu.cs:52-55 saute à BuiltInCodeSymbols.BIOSAfterDateIsSet = 0x2e1 ; LoadRom() charge le BIOS en ROM ; le jeu est lancé par le BIOS lui-même depuis le FS.
- Toi : initBiosRtc pose pc = 0x2E1 (main.zig:317) — identique.
Pourquoi : c'est le BIOS qui détient la logique du système de fichiers flash, la gestion de la date, la détection de bouton MODE pour le menu fichier, et surtout le lancement du jeu (écriture EXT pour basculer la banque d'instructions ROM→Flash, phase bios_game_launch 0x3AE). Démarrer directement sur le jeu court-circuiterait toute cette initialisation matérielle (SFR, timers, LCD) que le BIOS configure correctement.
Toutefois, ta version saute aussi les phases d'init BIOS 0x200-0x294 (RESET/clear RAM/post-init). DreamPotato ne saute que le query date (0x2E1) et les phases précédentes tournent normalement si PC démarre à 0. Chez toi, comme reset() met PC=0 puis initBiosRtc écrase à 0x2E1, tu contournes tout. Recommandation : laisse le BIOS démarrer depuis PC=0 (comme DreamPotato qui ne force 0x2E1 qu'au moment où la date est demandée, cf. Vmu.cs:52 « if Pc == 0 → jump », pas dès le reset). C'est très probablement une des raisons du souci d'affichage : les SFR réels (timers, LCD, interruptions) ne sont pas configurés par ton code invité comme le ferait le vrai BIOS.
En résumé : démarre sur le BIOS (pas directement sur le jeu), et cherche le gel d'écran d'abord dans le traitement de l'IRQ P3 (mode continuous / P31INT jamais effacée → tempête d'interruptions) et dans la lenteur de l'INT3 base-timer, avant de considérer le polling des touches une fois/frame. Tu pourrais aussi implémenter au minimum le gating du rafraîchissement (MCR bit3 / VCCR bit7) pour t'aligner sur libevmu si tu veux reproduire fidèlement le comportement d'affichage.
